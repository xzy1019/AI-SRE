## 1. Figure 1 "Denoising Rate (Mean ± Standard Deviation) for Each Experiment" —— Sees if "Analysis Layer Can Be Used"

**Why This Chart Matters**: The most painful part for on-call personnel is not "many incidents," but **20 alarms triggered by a single incident, each one treated as an independent event**. The goal of denoising is to converge N alarms into K incident clusters, **without conflating two different faults into one**.

### How to Read It

| Element | Meaning | What to Watch Out For |
|---|---|---|
| **Bar Length** | Denoising Rate = `1 − Number of Clusters / Number of Alarms` | Longer = Fewer alarms the on-call personnel need to look at |
| **Error Bars (±)** | Standard Deviation of Multiple Rounds of the Same Experiment | Shorter is more stable; longer error bars indicate a higher variability in the number of alarms generated by this fault |
| **Right Side "Top-1 x/y"** | Number of Rounds Where Root Cause was Correctly Identified | **Must be viewed together with the denoising rate** (see the trap below) |
| **Right Side "No Alarms n"** | Number of Rounds in This Experiment That Did Not Generate Any Alarms | These rounds **are not included** in the denoising rate statistics |

### Three Common Misinterpretations

1. **F04's Denoising Rate is 0% —— This is Not a Failure.**
   F04 (Postgres CPU Pressure) generated only **1 alarm**. The denominator for the denoising rate is the number of alarms, so "1 alarm with no noise to reduce" results in a 0% rate. **The denoising rate must be viewed together with the number of alarms**; looking at the percentage alone can lead to misjudgments.
2. **High Denoising Rate + Low Hit Rate = The Most Dangerous Situation.**
   Converging 20 alarms into 1 but incorrectly identifying the root cause is equivalent to **hiding the incident**. Therefore, this project displays **cluster purity, over-merge rate, candidate P/R, and Top-1** alongside the denoising rate — they are a set.
3. **Long Error Bars Do Not Indicate "Experiment Failure."**
   F01 (pod-kill) has the longest error bars (±37.5%), because the number of alarms generated by "killing a replica" is inherently unstable (depending on how fast the restart happens). This is a **fundamental attribute of the fault** and not a process issue.

### Corresponding Experimental Objectives

Each bar represents a different fault scenario. The differences between bars reflect the **different "fan-out" of incidents at the monitoring layer**:
- Pod-level faults (F06 Memory Pressure, F04 CPU Pressure) → Fewer alarms, smaller denoising potential
- Link/network-related faults (F05 Partition, F07 Extended Partition) → More alarms, greater denoising benefits

## 2. Figure 2 "Composition of Repetitive Rounds" —— Sees if the Conclusion is Stable

**Why this figure matters**: A single successful run may be accidental; repeated runs show whether the result is stable.
Project F06 had once "passed" a single run (producing 2 alerts), but after 3 consecutive runs, all three rounds had **zero alerts** — this is the pitfall recorded by P50.

### How to Read

| Element | Meaning |
|---|---|
| **Blue Segment** | The number of rounds in which the experiment **generated alerts** (evaluatable) |
| **Red Segment** | The number of rounds in which the experiment **generated no alerts** (non-evaluatable) |
| **Right-side Text** | `Evaluatable n / No Alert m` |

**How to read the colors**: The red segment means there was no input data for that round. It does **not** indicate an evaluation-script error.
The meanings are entirely different: the former is an engineering issue, while the latter is an **experimental design issue** (fault intensity or duration is insufficient to trigger an alert).

### The Most Worthwhile Line on the Figure: F06

The line for F06 shows **two segments side by side**: the first 3 rounds are all red, and the last 3 rounds are all blue. This tells a complete story:

1. Original Design: Memory pressure set to 200MB, while the container limit is 384MiB, and the application itself uses only ~30MiB
   → Combined 230MiB **does not reach the limit** → Whether OOM depends on luck → **3 rounds with zero alerts**
2. Localization: Measured the actual memory usage with cAdvisor, calculated "354MiB short of the limit to reach the limit"
3. Fix: Adjusted the pressure to **360MB** (≈ 93% of the limit) and added a new rule `ContainerMemoryHigh` (working set > 85% of the limit) — **no longer betting on whether it will be OOMKilled**
4. Retest: **3/3 rounds triggered**

So, this figure can instantly show "which experiment is truly reproducible and which one is just lucky."

## 3. Figure 3 "RAG Comparison" —— It Shows a "Negative Result"

**Why a "No Improvement" chart is included**: Negative results still show where additional work is needed.

### How to Read

| Element | Meaning |
|---|---|
| **Two Bars** | No RAG / RAG-enabled Top-1 Hit Rate |
| **Right-side Text** | The **average single-time duration** under this pattern |

**What You See on the Chart: The hit rates are the same (7/7 = 100%).**

### Why "No Gain" Is Worth Discussing

Initially, RAG was **found to be effective at a single point**: In F03 (order outward latency), without RAG it was judged as `payment` (wrong), and with RAG it was judged as `order` (right). But that conclusion was drawn when the **post-processing still had bugs** — at that time, topology folding would change the correct answer to the wrong one, and RAG made the model more confident, just enough to outweigh the folding.

Later, after fixing the folding (by adding a confidence guard) and补齐判责规则后，**F03 不带 RAG 也答对了**，整条链路在 7/7 上饱和。

**Conclusion: Structural fixes (at the rule layer + post-processing layer) are more effective than "giving the model more context."** The problem RAG aimed to solve has already been addressed by the preceding engineering fixes.

To demonstrate the value of RAG, a **more challenging benchmark** is needed: ① Compare after removing rule layer knowledge; ② Introduce unseen fault patterns; ③ Construct evidence with intentional ambiguity.

## 4. F13 / F14: Concurrent Multiple Failures (Merged into Matrix on 2026-11-04)

> **Update**: F13/F14 originally only had a single old dataset from 11-02 (with a duration of 180s and old rules). On 2026-11-04, they were **merged into the fault matrix and rerun 3 times each**, now appearing in Figures ① / ②, while the "non-matrix experiments" only retain historical datasets that have been replaced by new data (marked as [Historical: Replaced by New Data]).

**What these two experiments add**: They check the most error-prone part of denoising: merging related alerts without merging independent faults.

| Experiment | Fault Combination | True Root Causes | Examined Point |
|---|---|---|---|
| **F13** | payment full replica unavailable + order→payment delay + redis unavailable | payment, redis | A chain needs to be **merged into one cluster**; the independent root cause redis **cannot be merged in** |
| **F14** | payment + redis + postgres three independent root causes concurrently | payment, redis, postgres | The three are **parallel dependencies** (not a call chain), must be recognized as **3 root causes** instead of converging into 1 |

### How to Read

Similar to Figure ①, but **without error bars** (single run). Focus on two points:

1. **High denoising rate** (fewer alerts) — F13/F14 are both around 77%
2. **Over-merge rate must be 0** — This is a more dangerous error than "not enough denoising": Merging two independent faults into one cluster can cause on-call personnel to **miss one fault**.

**Post-Rerun Measurements (3 runs each):**

| Experiment | Rounds | Denoising Rate | Cluster Purity | **Over-merge** | Candidate P/R | Top-1 |
|---|---|---|---|---|---|---|
| F13 Cascade | 3 | 52.7%±11.3% | 82.8%±11.4% | **0%** | 1.00/1.00 | 3/3 |
| F14 Multi-Root Causes | 3 | 75.4%±2.1% | 50.0%±0 | **0%** | 1.00/1.00 | 3/3 |

**How to Interpret These Numbers**:

- **Over-merge = 0%** is the key column here: no two independent faults were merged into one cluster, which would hide one of them from on-call engineers.
- **Purity 50% / 82.8% does not indicate poor performance**: In multi-root cause scenarios, multiple candidates can naturally exist within a cluster (e.g., `{payment, redis, postgres}` are all true root causes). This is the口径 correction recorded in P16 — **the root causes in a cluster are the candidate set, not a single answer**.
- **Candidate P/R = 1.00/1.00** is the criterion for "no false positives and no false negatives".
- The denoising rate of F13 fluctuates significantly (±11.3%) while F14 is very stable (±2.1%): F13 contains **network delay** (alert count fluctuates with delay), while F14 consists of three **pod failures** (alert count is stable).

> For multi-root incidents, read the over-merge rate and candidate recall together; cluster purity alone is not enough.

## 5. One-Page Quick Reference: Four Metrics and Their Purposes

| Metric | Intuition | Manages What | Danger Direction |
|---|---|---|---|
| **Denoising Rate** | `1 − 簇数/告警数` | How much less a duty person **sees** | Too low → Too much noise |
| **Cluster Purity** | Proportion of primary candidates within a cluster | How **clean** a cluster is | Too low → Forced clustering |
| **Over-merge Rate** | Proportion of clusters containing root causes outside the GT in the candidate set | Whether **different faults are mixed together** | >0 is the most dangerous (can miss faults) |
| **Candidate Precision / Recall** | Whether the candidate set is correct | Whether **root causes are missed or wrongly attributed** | Recall <1 means missing root causes; Precision <1 means false positives |
| **Top-1 / MRR** | How accurate the first-ranked candidate is | **Sorting quality** | Low → Self-healing may target the wrong component |

> Read these values together: denoising rate shows how many alerts were removed; purity and over-merge rate show whether the merge was correct; candidate P/R shows whether any root cause was missed; Top-1 shows which service is checked first. Reporting the denoising rate alone is not enough. P16 showed that a cluster can contain a candidate set rather than one answer.
