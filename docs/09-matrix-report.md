## 2. 方法学：这一轮修掉的 4 个坑

跑第一遍时 6 个实验"全部产出数据集、汇总一行不缺"，看起来是成功的；实际全是错的数据。
四个坑都不是算法问题，而是**取数与编排**问题（详见 [06](06-pitfalls.md)）：

| # | 坑 | 识别信号 | 修法 |
|---|---|---|---|
| P31 | 实验背靠背跑，上一轮告警还没停就注入下一次 | `T_firing − T0` = **0~1 秒**（真实故障不可能这么快） | 每轮注入前加"告警窗口排空"闸门（`firing=0` 且 AM=0） |
| P32 | `matrix.jsonl` 缺换行 → 不是合法 JSONL | `wc -l` = 0，记录是 `}{` 直接拼接 | 写记录时显式 `fh.write("\n")`，旧文件用 `raw_decode` 切分重写 |
| P33 | 导出用"回看 12 分钟"，窗口越过 T0 | 实时轮询 170s 内**没** firing，导出却有 `firing 12` | 改用精确窗口 `[T0, now]`（脚本本就支持第 4/5 个参数） |
| P34 | 导出抢在 Alertmanager 投递之前 | Prometheus 里已 `firing`，数据集 **事件 0** | 导出前轮询等 `ingest_received_total` 严格变大 |

**这四条合起来说明一件事**：AIOps 项目里"数据看起来齐了"是最危险的假象——
必须用**交叉读数**（实时 Prometheus 查询 vs 落盘产物）互相校验，才能发现窗口串味与投递时延。

## 4. 盲区根因：三条规则文本与实测的错配

业务告警规则（`manifests/observability/_prometheus-rules.yml`）的实际条件：

| 规则 | 条件 | `for` |
|---|---|---|
| `DemoAppHighErrorRate` | `5m` 窗口 5xx 占比 > 5% **且** 该服务 QPS > 0.2 | 2m |
| `DemoAppDownstreamFailure` | `5m` 窗口下游错误速率 > 0.05/s | 2m |
| `DemoAppHighLatency` | `5m` 窗口 P95 > 1s（**只看 payment 自身**） | 3m |

对照实验时长与实测，三条错配：

1. **故障时长 < 判定时长。**
   F03/F05 的故障只有 **120s**，而规则要 `for: 2m`（=120s）**且**统计窗口是 `5m`。
   要在 120s 内"连续满足 2 分钟"，几乎没有余量；F04 是 150s，同样紧张。
2. **5 分钟速率窗口把短故障稀释了。** 120s 的故障落在 `rate(...[5m])` 里，
   前后 3 分钟的健康流量把比值拉低，更难越过 5% 阈值。
3. **"低流量保护"在故障时反过来压住告警。**
   `DemoAppHighErrorRate` 要求 `QPS > 0.2` 才判定（本意是避免低流量误报）。
   而 F05 恰好把 QPS 打到 **0.144 < 0.2** —— **故障越严重、流量越塌、这条规则越不会响**。
4. **F03 的观测点选错了。** 延迟加在 **order → payment 的出向路径**上，
   而 `DemoAppHighLatency` 只看 `service="payment"` 自身的 P95 ——
   拿 payment 自己的延迟去测一条**不在 payment 上**的路径，天然测不到。

### 4.1 用 F07 反证："规则是对的，是时长不够"

把同一个网络分区从 **120s 拉到 300s**（F07），其他不变：

```
第二轮 F07（21:27:44 注入，300s）
21:27:44  T0 注入（payment ↔ order 分区）
21:30:46  T_firing（注入后 182s）→ 告警进入 firing
21:30:46  等待 Alertmanager 投递：ingest 346 → 349（P34 的修复生效）
21:30:48  导出数据集：事件 3 / firing 1
          唯一 firing = DemoAppDownstreamFailure(order)，GT=payment-service → 经拓扑折到 payment
评测：告警 1 → 簇 1，降噪 0%（单条无噪可降），Top-1 命中 = 是

第一轮 F07（21:21:10 注入）作为 P34 的证据保留：
21:22:41  T_firing（91s），Prometheus 里 1 firing + 5 pending
21:22:43  导出 → 事件 0（抢在投递之前，见 P34）
```

**结论**：同一种故障，只要持续时间足够长，规则**会**正常触发。
所以 F03/F04/F05 的零告警**不是规则坏了**，而是
**"故障时长 / 观测点 / 阈值口径" 与 "规则判定条件" 不匹配**。

> **2026-11-03 更正**：后来发现 F03 还有更底层的原因 —— 它的 NetworkChaos 带了 `target`，
> 而业务走 Service ClusterIP，导致 **800ms 延迟根本没注入**（控制器却报 `AllInjected=True`）。
> 也就是说 F03 的旧结论「观测点选错」**只对了一半**，另一半是「故障压根没生效」。详见 [P42](06-pitfalls.md)。

## 5. 结论、行动项与局限

### 5.1 结论

1. **降噪与根因排序这一层是可信的**：有告警的 4 个实验，降噪 29.2%、纯度 100%、过度合并 0%、Top-1 100%、MRR 1.000。
2. **观测层有真实盲区**：6 个注入里 3 个（50%）在监控侧完全静默；其中 1 个（F05）已用实测证明业务确实受损。
3. **"零告警"必须先排除方法学原因**：时长、窗口、投递时延、观测点，四者任一不匹配都会制造假盲区。

### 5.2 行动项

| # | 动作 | 依据 |
|---|---|---|
| 1 | 混沌实验的 `duration` **统一 ≥ 6 分钟**（覆盖 5m 窗口 + 2m for） | 4.1 F07 验证 |
| 2 | 为**流量塌陷型**故障补规则：不依赖 QPS 下限，改看 `QPS 相对基线的跌幅` | F05：QPS 5.69 → 0.144 |
| 3 | 延迟类规则按**调用边**（service → downstream）建，而不是只看被调方自身 | F03 观测点错位 |
| 4 | 补 postgres/redis 的**依赖延迟与资源**规则 | F04 全程 5xx=0、无任何规则覆盖 |
| 5 | 导出窗口改为 `[T0, 故障结束 + 余量]`；目前快速 firing 的实验窗口偏短（见 §5.3） | F01 窗口仅 31s |

### 5.3 局限（如实记录）

- **快速 firing 的实验，指标窗口偏短**：导出在"首次 firing"时就执行，
  于是 F01 的 `metrics.json` 只有 31s、F06 只有 15s。事件（告警流）不受影响，
  但**指标曲线不足以看恢复过程**。修法见行动项 5。
- **F01/F03/F04 未能独立确认"注入是否生效"**：F03/F04 的 SLI 恰恰是"没覆盖到"的那部分，
  所以"零告警"里混着"可能没注入"与"确实没规则"两种可能；F05 因为有 QPS 塌陷的硬证据，才能定论。
- **单次运行**：每个实验目前只有 1 个样本，尚无重复性统计（下次可跑 3 遍看稳定性）。

被调方自身延迟正常 ⇒ 责任在调用方出向路径；被调方自己也不健康 ⇒ 顺链下沉。
事件流里目前没有这条信息 → 记为下一步。

### 6.5 边类告警"判责"（2026-11-03 追加）

§6.4 留下的问题：**F03 的候选集合对了（召回 1.0），但排第一的是谁判断不对**。
根因是"`order→payment 变慢`"这条告警本身**没有携带"被调方健不健康"的信息**，
降噪层只能猜。于是把判断**前移到规则层**：

```promql
# 边延迟高  AND  被调方自身服务端 P95 正常（<1s）
histogram_quantile(0.95, sum by (le,service,downstream,ground_truth)(
  rate(downstream_duration_seconds_bucket{job="demo-app"}[2m]))) > 0.5
and on(downstream)
label_replace(
  histogram_quantile(0.95, sum by (le,service)(
    rate(http_request_duration_seconds_bucket{job="demo-app"}[2m]))) < 1,
  "downstream", "$1", "service", "(.+)")
```

含义：**被调方自己没变慢 ⇒ 责任在调用方的出向路径/这条边**；
被调方也慢、或根本没有请求（分区时 `rate=0 → histogram_quantile=NaN`，右侧无序列）⇒ 这条边的延迟只是下游故障的**症状**，不再独立成"边故障"告警。

降噪层对应收敛：该告警出现即证明"被调方健康"，因此候选 = **调用方**（不再给两端，避免把已被证据排除的被调方算作候选）。

**效果：**

| 指标 | P43 后 | 判责后 |
|---|---|---|
| 簇纯度 | 78.6% | **85.7%** |
| 候选精确率 | 0.81 | **0.86** |
| 候选召回率 | 1.00 | **1.00** |
| Top-1 命中率 | 85.7% | **85.7%** |
| MRR | 0.857 | **0.893** |

F05（payment 分区）的边延迟告警从 5 条降到 1 条 —— 被调方确实不健康时不再产出"边故障"告警。

#### 6.5.1 追加：边瓶颈截断 + 错误闸门（当天再闭环）

上面留下的"F03 的 Top-1 仍是 payment"，根因是 **"沿链下沉"的系统性偏差**：
级联症状（frontend 错误率、frontend→order 调用失败…）会沿拓扑**一路下沉到链尾 payment**，
把 payment 的分数堆到 7.0，而真正的瓶颈 order 只拿到 1 条边告警的 2.0。

两处修正：

| # | 改动 | 说明 |
|---|---|---|
| 1 | **边瓶颈截断**（降噪层） | 既然边告警已证明"被调方健康"，那么**穿过这条边的症状就不该继续下沉** —— 截断在该边的**调用方**。`self` 类证据（如 `DemoAppScrapeDown(payment)`）不截断，避免把真根因抹掉 |
| 2 | **错误闸门**（规则层） | 边延迟告警再加一条"**这条边不能同时在报错**"（`downstream 错误率 < 0.05/s`）。慢 + 错 = 下游挂了，属于"下游故障"而非"边/出向路径故障" |

第 2 条的必要性：F05（分区）**恢复期**被调方一度恢复服务，2m 窗口里旧的高延迟让边告警又 firing 了一次，
结果把 F05 的归因带偏到 order。加闸门后该告警在 F05 里彻底不出现。

**最终结果（7/7）：**

| 指标 | 判责前 | **最终** |
|---|---|---|
| 簇纯度 | 85.7% | **100.0%** |
| 过度合并率 | 21.4% | **0.0%** |
| 候选精确率 / 召回率 | 0.86 / 1.00 | **1.00 / 1.00** |
| Top-1 精确率 / MRR | 0.86 / 0.893 | **1.00 / 1.000** |
| **Top-1 命中率** | 85.7% | **100%（7/7）** |

行为验证：**F03 保留 1 条边延迟告警**（被调方健康、边不报错 → 责任在调用方出向路径）；
**F05 为 0 条**（边在报错 → 属于下游故障，由失败告警负责）。

### 6.7 RAG 全矩阵 A/B 对照（2026-11-03 追加）—— 一个诚实的**负结果**

此前 RAG 只在 F03 单点上验证过（Top-1 由 `payment` 纠正为 `order`）。扩到全矩阵后：

| 指标 | 无 RAG | 带 RAG |
|---|---|---|
| **Top-1 命中** | **7/7（100%）** | **7/7（100%）** |
| 平均耗时 | 3.3s | 3.2s |
| 检索命中 | — | 见下表 |

| 实验 | GT | 无 RAG | 带 RAG | 检索到的历史案例 |
|---|---|---|---|---|
| F01 | payment | payment | payment | P01, P02 |
| F02 | payment | payment | payment | P17, P21 |
| F03 | order | **order** | **order** | **P45, P43**（高度相关） |
| F04 | postgres | postgres | postgres | P43, P16 |
| F05 | payment | payment | payment | P43, P17 |
| F06 | payment | payment | payment | P01, P02 |
| F07 | payment | payment | payment | P13, P43 |

**结论（要如实说）：在当前矩阵上，RAG 没有可测量的增益。** 原因是**天花板效应**：

1. 当初测到"RAG 把 F03 从错纠正为对"，是在 **P49 折叠 bug 修好之前** —— 那时后处理会把正确答案改错，RAG 让 LLM 更坚定，恰好压过了折叠。
2. P49 修好（加置信度守卫）后，**F03 不带 RAG 也已经答对**；再加上 P45/P43 把判责与候选模型都补上了，整条链已经在 7/7 上饱和。
3. 也就是说：**结构性修复（规则层 + 后处理层）比"给模型更多上下文"更有效**——RAG 想解决的问题，已经被前面的工程修复解决了。

**顺带观察到的检索质量问题**：命中相关度**参差不齐**——
F03 检索到 P45（边类告警不带判责）**非常贴切**；但 F01/F06 检索到的是 P01/P02（告警规则没生效 / 直方图二次累积），
与"pod-kill / 内存压力"这两个故障**并不相关**。说明当前检索（bge-m3 + 单条拼装 query）在**故障类型差异大**时召回质量不稳定。

**要真正评估 RAG，需要更难的基准**：例如① 把规则层与后处理的知识**移除**后再对比；② 引入**未见过的故障形态**（LLM 无法从证据直接推出、必须依赖历史经验）；③ 构造**故意歧义**的证据。这三者当前矩阵都不具备。
