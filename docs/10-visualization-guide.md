## 0. 先明确：这个项目要证明什么

项目关注的是从故障注入、根因定位到自愈执行的完整链路。每一步都有实测数字，并与其他观测结果交叉验证，而不只是检查组件是否安装。

图表页的三张图，分别对应这条链路上**三个不同的问题**：

| 图 | 回答的问题 | 对应项目目标 |
|---|---|---|
| ① 各实验降噪率 | 告警被收敛掉多少？收敛得**对不对**？ | 分析层能不能用 |
| ② 重复轮次构成 | 这些结论**稳定**吗？换个轮次还成立吗？ | 结论可不可信 |
| ③ RAG 对照 | 加"历史经验检索"有没有**额外**收益？ | 该往哪投入 |
| ④ 非矩阵实验 | 还有哪些数据集不在矩阵里？ | 不漏掉历史资产 |

## 1. 图①「各实验降噪率（均值 ± 标准差）」—— 看的是"分析层能不能用"

**这张图的作用**：值班场景中常见的负担是一次故障刷出 20 条告警，每条都像独立事件。
降噪要做的就是把 N 条告警收敛成 K 个事件簇，**而且不能把两个不同的故障揉成一个**。

### 怎么读

| 图元 | 含义 | 该注意什么 |
|---|---|---|
| **条形长度** | 降噪率 = `1 − 簇数/告警数` | 越长 = 值班人要看的条数减少得越多 |
| **误差棒（±）** | 同一实验多轮的**标准差** | 越短越稳定；长误差棒说明这个故障形态产生的告警数波动大 |
| **右侧 "Top-1 x/y"** | 根因排序命中的轮数 | **必须和降噪率一起看**（见下面的陷阱） |
| **右侧 "无告警 n"** | 该实验有几轮压根没产生告警 | 这些轮次**不计入**降噪率统计 |

### 三个容易误读的地方

1. **F04 的降噪率是 0% —— 这不是失败。**
   F04（postgres CPU 压力）只产生了 **1 条**告警。降噪率的分母是告警数，"1 条告警无噪可降"，
   所以 0% 是**正确**结果。**降噪率必须和告警条数一起看**，单看百分比会误判。
2. **高降噪率 + 低命中率 = 最危险的情况。**
   把 20 条告警收敛成 1 条、但根因判错了，等于**把故障藏起来了**。
   所以本项目把 **簇纯度、过度合并率、候选 P/R、Top-1** 和降噪率并列展示 —— 它们是一组。
3. **误差棒长不等于"实验没做好"。**
   F01（pod-kill）的误差棒最长（±37.5%），因为"杀掉副本"产生的告警条数本身就不稳定
   （取决于重启快慢）；这是**故障形态的固有属性**，不是流程问题。

### 对应的实验目的

每根条 = 一种故障形态。条形之间的差异，反映的是**不同故障在监控侧的"扇出"不同**：
- 单个 Pod 层面故障（F06 内存压力、F04 CPU 压力）→ 告警少，降噪空间小
- 链路/网络类故障（F05 分区、F07 加长分区）→ 告警多，降噪收益大

## 2. 图②「重复轮次构成」—— 看的是"结论稳不稳"

**这张图用于检查重复性**：单次跑通可能来自偶然，连续多轮才能说明结论是否稳定。
本项目 F06 曾经"跑通过"（单轮产生过 2 条告警），但连跑 3 轮后**三轮全部零告警** —— 这就是 P50 记录的坑。

### 怎么读

| 图元 | 含义 |
|---|---|
| **蓝色段** | 该实验**产生告警**的轮数（可评测） |
| **红色段** | 该实验**一条告警都没产生**的轮数（不可评测） |
| **右侧文字** | `可评测 n / 无告警 m` |

**区分**：红色表示这一轮没有输入数据，**不是评测脚本报错**。
两者含义完全不同：前者是工程问题，后者是**实验设计问题**（故障强度/时长不足以触发告警）。

### F06：重复运行后的差异

F06 那一行会看到**两个色块并列**：前 3 轮全红、后 3 轮全蓝。它讲的是一个完整的故事：

1. 原设计：内存压力 200MB，而容器 limit 是 384MiB、应用自身只用 ~30MiB
   → 合计 230MiB **压不到 limit** → 是否 OOM 全看运气 → **3 轮全部无告警**
2. 定位：用 cAdvisor 量出真实内存占用，算出"差 354MiB 才能碰到 limit"
3. 修法：压力调到 **360MB**（≈ limit 的 93%），并新增规则
   `ContainerMemoryHigh`（工作集占 limit > 85%）—— **不再赌"是否恰好被 OOMKilled"**
4. 复验：**3/3 全部触发**

所以这张图一眼能看出"**哪个实验是真的可复现，哪个是靠运气**"。

## 3. 图③「RAG 对照」—— 看的是一个"负结果"

**为什么保留一张"没有改善"的图**：负结果同样是结论，它决定了下一步该往哪投入。

### 怎么读

| 图元 | 含义 |
|---|---|
| **两根条** | 无 RAG / 带 RAG 的 Top-1 命中率 |
| **右侧文字** | 该模式下的**单次平均耗时** |

**图上看到的是：两者命中率相同（7/7 = 100%）。**

### 为什么"没有增益"反而值得讲

当初 RAG 是**在单点上测出有效**的：F03（order 出向延迟）里，不带 RAG 判成 `payment`（错），
带 RAG 判成 `order`（对）。但那个结论是在**后处理还有 bug 的时候**测的 ——
当时拓扑折叠会把正确答案改错，RAG 让模型更坚定，恰好压过了折叠。

后来修掉折叠（置信度守卫）并补齐判责规则后，**F03 不带 RAG 也答对了**，整条链路在 7/7 上饱和。

**结论：结构性修复（规则层 + 后处理层）比"给模型更多上下文"更有效。**
RAG 想要解决的问题，已经被前面的工程修复解决了。

要让 RAG 体现出价值，需要**更难的基准**：① 把规则层知识移除后再对比；② 引入未见过的故障形态；③ 构造故意歧义的证据。

## 4. F13 / F14：多故障并发（2026-11-04 已并入矩阵）

> **更新**：F13/F14 原来只有 11-02 的**单次旧数据**（当时是 180s 时长、且用的旧规则）。
> 2026-11-04 已把它们**并入故障矩阵并各重跑 3 轮**，现在它们出现在图① / 图② 里，
> 而"非矩阵实验"图只保留真正没进矩阵的历史数据集（标了 `[历史：已被新数据取代]`）。

**这两个实验用于检查降噪最容易出错的部分**：该合的告警要合，不该合的不能合。

| 实验 | 故障组合 | 真实根因 | 考察点 |
|---|---|---|---|
| **F13** | payment 全副本不可用 + order→payment 延迟 + redis 不可用 | payment, redis | 一条链要**合并成一个簇**；独立根因 redis **不能被并进去** |
| **F14** | payment + redis + postgres 三个独立根因并发 | payment, redis, postgres | 三者是**并列依赖**（非调用链），必须识别成**3 个根因**，而不是收敛成 1 个 |

### 怎么读

和 图① 同样口径，但**没有误差棒**（单次运行）。重点看两点：

1. **降噪率要高**（少看告警）——F13/F14 都在 77% 左右
2. **过度合并率必须为 0** —— 这是比"降噪不够"更危险的错误：
   把两个独立故障揉成一个簇，会让值班人**漏掉一个故障**。

**重跑后的实测（各 3 轮）：**

| 实验 | 轮数 | 降噪率 | 簇纯度 | **过度合并** | 候选 P/R | Top-1 |
|---|---|---|---|---|---|---|
| F13 级联 | 3 | 52.7%±11.3% | 82.8%±11.4% | **0%** | 1.00/1.00 | 3/3 |
| F14 多根因 | 3 | 75.4%±2.1% | 50.0%±0 | **0%** | 1.00/1.00 | 3/3 |

**怎么读这两个数字**：

- **过度合并 = 0%** 是这里最关键的一列 —— 说明**没有把两个独立故障揉成一个簇**（那会让值班人漏掉一个故障）。
- **纯度 50% / 82.8% 不代表做得差**：多根因场景下，一个簇里本来就会出现多个候选
  （例如 `{payment, redis, postgres}` 同时都是真根因）。这正是 P16 记录过的口径修正 ——
  **一个簇的根因是候选集合，不是唯一答案**。
- **候选 P/R = 1.00/1.00** 才是"没有漏、没有冤枉"的判据。
- F13 的降噪率波动较大（±11.3%）而 F14 很稳（±2.1%）：F13 里含**网络延迟**（告警条数随延迟抖动），
  F14 是三个 **pod-failure**（告警条数稳定）。

> 多根因实验不能只看纯度，还要同时检查过度合并率和候选召回率。

## 5. 一页速查：四个指标各管什么

| 指标 | 公式直觉 | 管什么 | 危险方向 |
|---|---|---|---|
| **降噪率** | `1 − 簇数/告警数` | 值班人**少看多少** | 太低 → 噪音多 |
| **簇纯度** | 簇内主候选占比 | 一个簇**干不干净** | 太低 → 硬凑 |
| **过度合并率** | 候选里出现 GT 之外根因的簇占比 | **有没有把不同故障揉一起** | **>0 最危险**（会漏故障） |
| **候选精确率 / 召回率** | 候选集合对不对 | **漏根因 / 冤枉别人** | 召回 <1 会漏；精确 <1 会误伤 |
| **Top-1 / MRR** | 排第一的准不准 | **排序质量** | 低 → 自愈会打错目标 |

> 判读方式：降噪率表示减少了多少条告警；纯度和过度合并率检查合并是否正确；候选 P/R 用于发现漏报；Top-1 表示系统优先检查哪个服务。
> 只报降噪率是不够的 —— 那正是 P16 记录过的教训（一个簇的根因是**候选集合**，不是唯一答案）。
